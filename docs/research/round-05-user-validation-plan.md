# 深度调查第5轮：梗称号用户接受度与误伤测试方案设计（Explorer）

> **轮次**：Explorer Round 5 — 用户验证与误伤防线
> **状态**：Draft
> **日期**：2026-07-24
> **目标**：设计无需编造用户数据的梗称号接受度/误伤测试方案，覆盖老玩家/新玩家、位置玩家、赛事观众/主播观众、开启自嘲与否四个分层维度；输出可执行的问卷、A/B 测试、理解正确率、分享意愿、冒犯率、误读率、称号解释点击率、下线阈值等量化指标；选出 15–20 个代表梗提出假设但明确标注未实测。
>
> **特殊验证**：
> 1. 马头为何即使用户认为有梗也不宜自动授予
> 2. 左手/右手语义纠错是否降低传播

## 0. 方法论：四层用户分层

### 0.1 分层逻辑

用户对梗称号的接受度高度依赖其对 LOL 社区文化的参与深度和身份认同。单一整体测试会淹没关键差异。本方案按四个维度交叉分层：

```
                     ┌─────────────┐
                     │  用户分群    │
                     ├──────┬──────┤
                     │ 分层 │ 关键 │
                     │ 维度 │ 差异 │
           ┌─────────┼──────┴──────┼─────────┐
           │         │             │         │
      ┌────┴────┐ ┌──┴──┐ ┌──────┴──────┐ ┌─┴────┐
      │游戏经验 │ │位置 │ │ 内容消费    │ │自嘲  │
      │         │ │     │ │ 习惯        │ │模式  │
      ├─────────┤ ├─────┤ ├─────────────┤ ├──────┤
      │老玩家   │ │上单 │ │赛事观众     │ │开启  │
      │≥3年     │ │打野 │ │≥2场/周     │ │      │
      ├─────────┤ ├─────┤ ├─────────────┤ ├──────┤
      │新玩家   │ │中单 │ │主播观众     │ │关闭  │
      │<3年     │ │     │ │≥2h/周     │ │(默认)│
      │         │ ├─────┤ ├─────────────┤ │      │
      │         │ │ADC  │ │双修/都有    │ │      │
      │         │ ├─────┤ ├─────────────┤ │      │
      │         │ │辅助 │ │都不怎么看   │ │      │
      └─────────┘ └─────┘ └─────────────┘ └──────┘
```

### 0.2 关键假设（入口分层，非推测用户心理）

1. **游戏经验分层**的区分能力：新玩家对选手/主播梗认知度低，但可能对行为描述类称号（如"团战发动机"）接受度更高。老玩家更敏感于"梗是否用对了地方"。
2. **位置分层**的区分能力：被授予自己主位置以外的梗（如辅助被授予"奇迹行者"）触发误伤风险更高。
3. **内容消费分层**的区分能力：赛事观众对官方/解说梗接受度更高；主播观众对直播梗接受度更高；只看社区不看不代表不接受。
4. **自嘲模式分层**的区分能力：开启自嘲的用户对调侃型称号的接受度显著更高，但冒犯阈值可能因"我先自嘲了所以我更敏感"而出现非单调变化（详见 §6）。

### 0.3 测试禁忌

- **不编造用户数据**：不模拟"用户对局数据"，所有测试基于**展示梗称号 + 用户反馈**，不涉及"这个称号是根据你的数据生成的"。
- **不欺骗用户**：不给用户虚假的"你被授予了 X"的幻觉。测试场景均为"假设你获得了此称号……"的假设题或"A/B 版报告对比"。
- **不诱导负反馈**：冒犯率、误读率等采用**中性提问+开放回答**模式，而非直接"你感到被冒犯了吗？"注意效度。

## 3. 六项测试工具详细设计

### 3.1 T1 理解正确率测试

**目标**：每条梗的字面含义是否被目标用户正确理解。

**测试形式**：在线问卷，每个受访者随机分配 5 条梗（避免疲劳）。

**问题设计**（每梗 3 题）：

```
Q1：你觉得「{称号名称}」是什么意思？
A. 夸赞这个玩家打得好
B. 调侃/开玩笑说这个玩家打得有特点
C. 嘲讽/批评这个玩家打得不好
D. 描述这个玩家的打法风格（中性）
E. 不确定/看不懂
（正确选项由研究的语义分类定义，如"天神下凡"=A，"奇迹行者"=B）

Q2：如果你在游戏报告中看到这个称号，你会觉得系统在？
A. 夸我
B. 开玩笑
C. 批评我
D. 客观描述我
E. 不确定

Q3：你觉得这个称号适合用来描述一个（单选题）？
A. 打得非常好的玩家
B. 打得有特色的玩家（有好有坏）
C. 打得不太好的玩家
D. 有特定打法风格的玩家（不分好坏）
E. 不确定
```

**评分方式**：
- **理解正确率** = Q1 选项与预期 sentiment 一致的比例
- **感知偏差** = Q1/Q2 跨题的语义距离（如 Q1 选"夸赞"但 Q2 选"批评我" → 认知冲突）
- **模糊率** = Q1 选 E 的比例

**样本要求**：每梗 ≥ 50 份/层，按 §0.1 四个分层加权。总样本约 20 梗 × 50 = 1000 份/层，总样本约 4000 份。

**下线阈值**：`理解正确率 < 60%` → 降级或淘汰（如"右手"可能新玩家理解率低于此线）。

---

### 3.2 T2 冒犯率/误读率测试

**目标**：是否有非预期的负面情绪或歧义解读——这是误伤防线的核心工具。

**测试形式**：在线问卷，随机分配 5 条梗。每条梗使用 **中性引导 + 七点量尺 + 开放回答** 模式。

**问题设计**：

```
引导语（中性，不使用"冒犯"一词）：
"以下是 LOL 游戏报告中的一个称号：「{梗名称 + 简短展示文案}」

Q1：你看到这个称号时的第一感觉是？
1 ─ 2 ─ 3 ─ 4 ─ 5 ─ 6 ─ 7
很高兴  无所谓   很不舒服
（1-3=正面/中性，4=中立，5-7=负面）

Q2：你觉得这个称号可能会让被授予的玩家感觉被？
（可多选）
□ 被夸赞了
□ 被开了一个友好的玩笑
□ 被善意调侃了
□ 被系统评判了
□ 被嘲讽了
□ 被冒犯了
□ 被侮辱了
□ 说不清

Q3（开放题，非必填）：你还有别的想说的吗？
```

**误读率测量**（关键指标）：

```
误读率 = 填写者认为称号"在批评玩家"的比例
        （Q2 选中"被嘲讽/被冒犯/被侮辱"的比例）÷ 总样本

分层误读率 = 按用户分层统计上述比例，识别哪一层误读率最高
```

**冒犯率测量**（严格定义）：

```
主动冒犯率 = Q1 得分 ≥ 6 的比例（"很不舒服"侧）
被动冒犯率 = Q2 选中"被冒犯了"的比例（即使 Q1 ≤ 4）

联合冒犯率 = (主动冒犯率 + 被动冒犯率) / 2
            （更稳定的综合指标）
```

**样本要求**：每梗 ≥ 100 份/层，各层 ≥ 25 份。总样本约 20 × 100 = 2000 份/层，总约 8000 份。

**特殊设计——对照组校准**：

包含 V-17（及时雨送姜）和 V-18（马头）作为已知高风险对照。这两项的冒犯率应显著高于其他项。如果测试结果显示"马头"冒犯率低于预期（如用户因"有梗"而宽容），这恰好是 §7 要讨论的核心发现。

### 3.3 T3 分享意愿测试

**目标**：用户是否愿意将这个称号分享（展示给好友、社交网络）？

**测试形式**：在线问卷 + 概念测试。

**问题设计**：

```
假设你得到了「{称号名称}」这个称号。以下是三种场景：

场景A — 展示在自己的游戏主页上：
Q1：你愿意把这个称号展示在自己的个人主页上吗？
1─2─3─4─5─6─7
非常不愿意                 非常愿意

场景B — 发到朋友圈/微博/动态：
Q2：你会主动把这个称号截图发到社交媒体吗？
1─2─3─4─5─6─7
绝对不会           可能会            肯定会

场景C — 看到好友有这个称号：
Q3：如果你看到好友的称号是「{称号名称}」，你的第一反应是？
□ 会心一笑，觉得有趣
□ 截图发群里吐槽/调侃
□ 觉得系统在针对他
□ 觉得系统不准
□ 无所谓
□ 其他：______
```

**计算方式**：

```
分享意愿指数 = (Q1 均值 + Q2 均值 + Q3 正向选项比例) / 3
             （0-7 分，≥ 5 = 优秀，3-5 = 可用，< 3 = 不宜展示）

自嘲组 vs 默认组分享意愿差异 = 按自嘲开关分层的意愿差值
```

**样本要求**：每梗 ≥ 50 份/层。

---

### 3.4 T4 A/B 展示测试

**目标**：不同展示方式（文案/解释/位置）对接受度和分享意愿的影响。

**测试形式**：在线原型测试（Mockup）——展示两版游戏报告截图（A/B），用户对比后选择偏好。

**三个实验**：

#### 实验 1：解释文案（Explain）的有无

| 变体 | 展示方式 |
|:----:|---------|
| **A** | "你的称号是：奇迹行者"（无解释） |
| **B** | "你的称号是：奇迹行者 —— 你的参团率低于同段位玩家，刷野量高于同段位玩家。有句老话：奇迹行者还在刷野！"（含解释） |

**假设**：B 的理解正确率更高、误读率更低、分享意愿不变或略高（解释消除歧义）。

#### 实验 2：展示位置的权重

| 变体 | 展示位置 |
|:----:|---------|
| **A** | 报告顶部 Hero 区（大号称号+解释） |
| **B** | 报告底部"彩蛋"区（小号称号，无解释） |

**假设**：B 的冒犯率更低（不突出的展示减少"系统在评判我"的感觉），但分享意愿也可能降低（不显眼就不分享）。

#### 实验 3：自我贬损梗的展示措辞

| 变体 | 展示措辞 |
|:----:|---------|
| **A** | "你的报告称号是：4396！"（直接展示） |
| **B** | "本局趣味洞察：你的伤害占比较低。老玩家可能会想到一个数字——4396。"（间接引用） |

**假设**：B 的冒犯率显著低于 A（4396 为负面梗，间接引用降低"系统在批评我"的感受）。

**样本要求**：每组对比 ≥ 200 用户（100 A + 100 B），自嘲/非自嘲各半。

---

### 3.5 T5 称号解释点击率测试

**目标**：用户对"为什么给我这个称号"的主动了解意愿。

**测试形式**：在 Mockup 报告中加入"为什么是这个称号"的链接/按钮，测量点击率。

**问题设计**：

```
Mockup 报告界面：
┌─────────────────────────────────────┐
│  你的报告称号：奇迹行者              │
│  [为什么是这个称号？ →]             │ ← 可点击链接
│  [查看原梗出处 →]                   │ ← 可点击链接
│  [我不喜欢这个称号，换一个 →]        │ ← 可点击（仅测试用）
└─────────────────────────────────────┘
```

**测量指标**：

```
解释点击率 = 点击"为什么是这个称号"的用户比例
原梗点击率 = 点击"查看原梗出处"的用户比例
更换点击率 = 点击"换一个"的用户比例（负面信号）

解释完成率 = 点击后阅读了完整解释的用户比例
            （需要页面停留时间 ≥ 10 秒）
```

**分层分析**：
- 新玩家 vs 老玩家的解释点击率差异（新玩家需要更多解释）
- 正面梗 vs 负面梗的解释点击率差异（负面梗更需要解释？）
- 自嘲组 vs 默认组的更换点击率差异

**样本要求**：每梗 ≥ 200 用户。

**下线阈值**：
- `更换点击率 > 30%` → 需要重新评估该梗的适合性
- `解释点击率 < 10%` 且 `理解正确率 < 60%` → 用户不想了解这个梗，但也不理解 → 淘汰

---

### 3.6 T6 下线阈值标定

**目标**：各类负面指标达到什么水平时，必须下线/降级/修改？

**决策矩阵**：

| 指标 | 绿色（安全） | 黄色（警告） | 红色（下线） |
|------|:-----------:|:-----------:|:----------:|
| T1 理解正确率 | ≥ 80% | 60–79% | **< 60%** |
| T2 主动冒犯率 | < 5% | 5–15% | **> 15%** |
| T2 被动冒犯率 | < 8% | 8–20% | **> 20%** |
| T2 误读率（批评解读） | < 10% | 10–25% | **> 25%** |
| T3 分享意愿指数 | ≥ 5.0 | 3.0–4.9 | **< 3.0** |
| T5 更换点击率 | < 10% | 10–30% | **> 30%** |
| T5 解释点击率 | ≥ 30% | 15–29% | **< 15%** |
| 分层差异（最高层 — 最低层 的冒犯率差） | < 10% | 10–20% | **> 20%** |

**复合判定规则**：

```
def should_takedown(result):
    reds = count_red(result)
    yellows = count_yellow(result)
    greens = count_green(result)

    if reds >= 3:
        return "IMMEDIATE_TAKEDOWN"
    if reds == 2 and yellows >= 2:
        return "TAKEDOWN"
    if reds == 1 and yellows >= 3:
        return "REQUIRE_MODIFICATION"
    if reds == 0 and yellows <= 2:
        return "SAFE"
    return "MONITOR"
```

**特殊规则**：
1. **不可降级替代**：D 级禁用梗不参与本阈值——不允许通过"修改文案"来规避红线（如"马头"修改为"小马驹"仍然是外貌关联）。
2. **分层保护**：即使总体指标为绿色，如果**某一分层的红色指标 ≥ 2 项**，必须为该层设计豁免机制（如"新玩家不展示该梗"）。
3. **时间衰减**：A/B 测试上线后 30 天重新测量一次——如果冒犯率随时间上升（用户新鲜感消退后负面情绪增多），也触发阈值。

## 6. 自嘲开关的特殊验证

### 6.1 自嘲模式的非单调效应假设

自嘲开关（self-mock toggle）的设计逻辑：用户开启后，系统可以展示调侃/轻度负面的梗（B 级）。但存在一个反直觉的 **非单调效应**：

```
冒犯率
  ↑
  │      ┌──────────── 自嘲开启组
  │      │              （预期两条线重叠，
  │      │               但 §6.2 解释为何可能不重叠）
  │      │
  │      └──────────── 默认组（关闭）
  │
  └─────────────────────────────→ 梗的负面程度
       低（正面）          高（负面）
```

**假设 H1（单调）**：自嘲开启用户的冒犯率在任何档位都低于默认用户。这支持"自嘲开关有效"。

**假设 H2（非单调）**：自嘲开启用户在 **轻度调侃区** 冒犯率低于默认用户，但在 **中等负面区**（如 4396）冒犯率反而升高——因为"我已经自嘲了，系统还要用 4396 来嘲笑我，太过分了"。如果 H2 成立，自嘲开关的设计需要重新考虑——它可能只有在"纯正面"和"轻度调侃"时有效。

### 6.2 验证方法

在 T2 测试中，将自嘲组和默认组的冒犯率对比绘制成曲线：

```
测试梗排序（按负面程度递增）：
天神下凡(正) → 雷达哥(正) → 厂长(正/调侃) → 肉蛋葱鸡(调侃)
→ 奇迹行者(调侃) → 369骰子(调侃) → 红温(teasing)
→ 正方形打野(中性) → 永远滴神(模糊)
→ 4396(负面) → 绝食流(负面隐喻) → 左手(模糊)

对每条梗分别计算：
  Δ冒犯率 = 自嘲组冒犯率 - 默认组冒犯率

如果：
- Δ 始终 < 0 → 单调有效（H1 成立）
- Δ 在某个区间 > 0 → 非单调（H2 成立）
```

### 6.3 自嘲开关的 UX 设计假设（待测试）

| 设计假设 | 预期效果 | T4 A/B 验证 |
|---------|---------|:-----------:|
| 默认关闭，手动开启 | 降低初期投诉率，但自嘲开启率低 | AB-02 |
| 默认开启，可在设置中关闭 | 自嘲开启率高，但可能初期有投诉 | AB-02（对照组） |
| 开启时弹窗解释"我们会展示一些圈内调侃梗" | 降低误读率，但可能增加开启门槛 | T1/T2 叠加验证 |
| 每个 B 级梗单独可屏蔽 | 用户控制感强，但操作复杂度过高 | T5 — 更换点击率可反映需求 |

## 7. 特殊验证一：马头为何即使用户认为有梗也不宜自动授予

### 7.1 核心论证链

马头是《深度调查》中争议最明确的梗——Round 1 即判定为 D 级禁用。但用户验证测试可能发现：**部分用户（尤其是 TheShy 粉丝或老社区成员）认为"马头"是一个有幽默感的梗，愿意被授予**。这恰好是需要在用户测试中验证并回应的。

以下为 **即使部分用户接受，也不应自动授予** 的五层论证：

#### 第 1 层：来源层 —— 黑称起源于外貌攻击，不可辩驳

```
┌─────────────────────────────────────────────────┐
│ 马头的原始出处：                                 │
│ - 由主播炫神推动，基于 TheShy 脸型（偏长）       │
│ - 被称为"马脸"的简化版                           │
│ - IG 官方曾投诉相关主播                         │
│ - LPL 官方对直播间使用此称呼发出警告             │
│ - 参考：维基百科、QQ News、维基学院             │
└─────────────────────────────────────────────────┘
```

**关键点**：这不是"语义演变"问题——马头从未失去其外貌攻击的起点。与"永远滴神"（从反讽变成半正面）不同，马头从未被去贬义化。

#### 第 2 层：数据层 —— 无游戏行为映射

马头不描述任何游戏行为。用问句检验：

> "一个玩家做了什么操作，会被授予'马头'？"

无法回答。而"天神下凡"（高光 carry）、"奇迹行者"（参团率低）都有明确的行为映射。马头**没有任何数据触发规则**——如果强行设定，只能是"使用 TheShy 常用英雄"或"打出类似 TheShy 的操作"，但这已经是"天神下凡"的触发区间，形成了**语义覆盖冲突**：

```
天神下凡 = TheShy 式高光（褒义、行为映射）
马头     = TheShy 式任何表现（外貌关联、无人身行为映射）

如果"TheShy 式表现"触发"马头"：
  → 用户打好了被骂"马头" → 荒诞
  → 用户打差了被骂"马头" → 人身攻击
  → 无论如何都不合理
```

#### 第 3 层：产品层 —— 系统授予 vs 社区使用的本质区别

```
社区中"马头"的使用场景：
- 弹幕刷屏（用户对用户）
- 直播间称呼（观众对主播）
- 论坛回帖（玩家对玩家）
→ 都是 P2P（个人对个人）的言论行为

产品中自动授予"马头"：
- 游戏报告（系统对用户）
- 系统生成的称号
→ 是 P2U（平台对用户）的官方行为

关键差异：
在社区中说"你是马头" = 一个用户的言论
系统说"你是马头"   = 产品在认证/认可这种称呼
```

**这就是"马头有梗但不宜自动授予"的核心原因**：平台不能将社区中最具攻击性的黑称合法化、系统化、自动化。即使 30% 的用户认为"有梗"，只要产品对剩下的 70% 造成了"官方在黑我"的感受，品牌伤害就是不可逆的。

#### 第 4 层：用户差异层 —— 接受度的不对称分布

假设 T2 测试显示以下分布：

```
老玩家 + TheShy 粉丝：80% 认为"马头"是梗，10% 感到冒犯
新玩家 + 非粉丝    ：20% 认为"马头"是梗，60% 感到冒犯
总体              ：45% 认为有梗，40% 感到冒犯
```

即使总体"有梗认知"率 > "冒犯率"（45% vs 40%），产品仍不应上线。原因：

1. **冒犯率 40% 在任何产品中都是不可接受的**。一般而言，超过 5-10% 的冒犯率已被认为是高风险。
2. **新玩家的 60% 冒犯率** 意味着这款产品对新手伤害极大——而新玩家是产品的增长引擎。
3. **"有梗认知"不等于"希望被授予"**。用户可能觉得"马头"有梗，但不希望自己被授予这个称号。

#### 第 5 层：防御层 —— 可预期的 PR 灾难路径

```
事件链：
1. 产品上线"马头"称号（即使加了自嘲开关）
2. 某玩家被系统授予"马头"称号
3. 该玩家（非 TheShy 粉丝）截图发微博："LOL 报告说我是马头？"
4. 大 V 转发："LOL 官方现在用黑称评价玩家？"
5. IG 官方/TheShy 粉丝抗议："这是黑称不是梗！"
6. 紧急下线 + 品牌道歉

这是一个可预见的 PR 灾难，任何冒犯率数据都无法排除此风险，
因为"系统授予黑称"这条新闻的传播力远超测试数据的统计学意义。
```

### 7.2 如果 T2 测试显示马头冒犯率低，该怎么解读？

| 可能的测试结果 | 解读 | 建议行动 |
|:-------------:|------|---------|
| 总体冒犯率 < 10% | 样本偏差——可能是老玩家 + 粉丝过度代表，或用户未理解问题的上下文 | 重新抽样，增加新玩家比例 |
| 新玩家冒犯率 < 15% | 新玩家根本不知道"马头"是什么梗 → 漠然 ≠ 接受 | 增加"马头"的解释暴露测试 |
| 老玩家冒犯率 < 5% | 老玩家社区内部去敏感化——圈内人觉得没问题，但对圈外人伤害不变 | 不以圈内数据为否决依据 |
| 自嘲组冒犯率 < 3% | 自嘲开启用户对一切都很宽容，不代表默认用户也宽容 | 坚持默认组数据为决策依据 |

**结论**：无论 T2 测试结果如何，"马头"都不应通过测试的绿色通道进入产品。其争议性测试的价值不在于"决定是否上线"（已决定不上线），而在于**验证本方案的分层保护机制是否有效**和**为后续类似梗的判定提供参照**。

## 8. 特殊验证二：左手/右手语义纠错是否降低传播

### 8.1 左手/右手的语义风险

左手（Knight）和右手（Chovy）在 Round 1 中评估为 positive/neutral，但存在两个特殊风险：

#### 风险 A：左撇子/右撇子的生理特征触发

```
"左手" = Knight 用左手操作鼠标（左撇子）
"右手" = Chovy 的镜像称呼

如果触发条件绑定"左手操作"（生理特征）：
→ 左撇子玩家被过多授予"左手"称号
→ 右撇子玩家几乎不可能获得"左手"
→ 产品层构成了对左右手握持方式的区别对待
→ 即使初衷不是歧视，效果上产生了"系统只给左撇子发称号"的偏差
```

#### 风险 B：新玩家的语义误读

```
新玩家看到"左手"：
→ "系统说我是左手？我右手操作啊？"
→ 将"左手"误解为"玩得不好/不协调"
→ 产生误读

新玩家看到"右手"：
→ "右手是什么意思？左手对应？"
→ 认知度更低 → 误读率更高
→ 在中文中"右手"也有"得力助手"的意思，
  可能与 LOL 的"左右手"梗产生混淆
```

### 8.2 语义纠错方案及其对传播的影响

#### 方案对比

| 方案 | 展示文案 | 解释文案 | 预期效果 |
|:----:|---------|---------|---------|
| **A（原样）** | "左手" | 无 | 最贴近原梗，但新玩家可能误读 |
| **B（加选手引用）** | "左手（Knight 式）" | "源自 Knight 的称号" | 明确指向选手梗，降低误读，但增加了认知门槛 |
| **C（行为重述）** | "对线压制者" | 不直接引用"左手" | 理解为行为描述，但失去了梗文化传播力 |
| **D（加解释）** | "左手" | "就像 Knight 一样，你的对线压制力一流" | 保留原梗+消除歧义，但额外 UI 空间需求 |

#### 假设：语义纠错对传播的影响

```
传播力（分享意愿 × 理解正确率）

高 ↑
   │   A（原样）──── 老玩家传播力高，但新玩家不分享
   │             \
   │  D（加解释）─── 折中方案：传播力略降但覆盖所有层
   │               \
   │  B（加引用）──── 认知门槛最高，传播力最低
   │                 \
低 │  C（行为重述）─── 完全失去梗文化，不建议
   │
   └────────────────────────────────→ 用户覆盖度
      只覆盖老玩家        覆盖全用户
```

**核心假设（待 T1+T3 验证）**：

1. 方案 D（加解释）的**传播力损失 ≤ 20%**（相比方案 A），但**理解正确率提升 ≥ 30%**（新玩家层）
2. 方案 B（加选手引用）对新玩家来说，"Knight 式"的引用是**信息噪音**而非上下文——认知负担增加，但理解正确率未必提升
3. 方案 C（行为重述）完全失去梗的传播价值——用户不会因为"对线压制者"而分享

### 8.3 右手梗的特殊风险

右手比左手多一层风险：

1. **认知度更低**：中文圈对 Chovy 的认知度远低于 Knight → 右手梗的底层支撑更弱
2. **中文歧义**：在中文中"右手"有多种含义（得力助手、右手边等），更容易被误读
3. **LCK 文化隔阂**：右手梗是 LPL 观众对 LCK 选手的"镜像命名"，LCK 观众不认可，中文圈内有"自嗨"批评

**假设**：右手梗的理解正确率可能 < 60%（已到 T6 下线阈值），且分享意愿可能 < 3.0（用户不认同/不分享）。

**建议**：如果 T1 验证显示右手梗理解正确率 < 60%，应**推迟右手单独上线**，改为将"左手"作为独立称号上线，配套解释文案："像 Knight 一样——对线压制力拉满。"

## 12. 风险与局限性

### 12.1 本方案已知局限

| 局限 | 影响 | 缓解 |
|:----:|:----:|:------|
| 问卷测试 vs 真实产品环境的差异 | 用户在问卷中的反馈可能与真实产品中不同（问卷更理性、产品中更情绪化） | Phase 4 灰度上线后重新测量 |
| 样本自选偏倚 | 愿意参加测试的用户群体可能对"梗"更感兴趣、接受度更高 | 用分层配额 + 招募时使用中性描述（不说"梗称号测试"） |
| 新玩家定义（< 3 年） | LOL 新玩家可能远少于老玩家，招募困难 | 通过 LOL 新手群/低段位渠道定向招募 |
| 自嘲开关在问卷中的模拟 | 问卷中让用户"假设开启了自嘲开关"与真实开关体验不同 | Phase 4 灰度用真实开关验证 |
| 跨文化的右手梗 | 右手梗的主要目标群体是关注 LCK 的中文观众，这个群体可能不易被问卷覆盖 | 在 NGA/LCK 相关板块定向招募 |

### 12.2 未覆盖的验证场景

- **线下/语音场景**：朋友一起看报告时，称号是否会产生额外的社交影响（被朋友嘲笑）？
- **长期接触效应**：连续 30 天收到同一个称号 vs 第一次收到的感受差异——新鲜感消退后，冒犯率可能上升。
- **竞争对手/陌生人场景**：称号被对手看到是否产生负面情绪（"对面的菜鸡被系统封为XXX"）？

这些场景建议在 Phase 4/5 灰度后作为独立测试加入。
